# ADR-0062: 回合写入顺序 —— 输出先落盘,再确认完成

- **状态**:Accepted
- **日期**:2026-08-22
- **关联**:ADR-0048(内容派生幂等键)、三库单写者不变量;2026-08 LangChain/LangGraph 工程调研

## Context

调研 LangGraph 时看到他们的 issue #8039:一个名为 `durability="sync"` 的开关,
两个写入丢进同一个线程池却**没有顺序屏障**,于是崩溃语义变成了**机器核数的函数**——
1 核容器恰好正确,16 核桌面必然重复。教训被总结成一句:

> **"同步"这个标签不写明顺序就等于没写。顺序本身就是崩溃语义。**

拿这条来审我们自己的回合循环,本以为只是"把既有的正确顺序写成文档 + 加个测试",
结果测试**发现顺序是反的**:

```
poll-loop.ts,result 事件处理块(修复前)
  markCompleted(initialBatchIds);   ← 先确认完成
  dispatchResultText(event.text);   ← 后写回复
```

两个写入都落在 **outbound.db**(容器是唯一写者,同步 SQLite 调用),所以这两行之间
崩溃是可能的:**消息被标记为已完成,而回复从不存在**。用户被永久的沉默回答,
而且**清扫器发现不了**——声明状态是 `completed` 而非卡住的 `processing`,
没有任何机制会重驱它。宿主自己的成本上限 / SLA `killContainer` 可以恰好落在这个窗口里。

这是一个 at-most-once 的洞,开在一个整体 at-least-once 的系统上。

## Decision

> **回合的输出必须先在 outbound.db 落盘,然后才确认完成。** 顺序不可颠倒。

两个方向的崩溃后果不对称,这就是选择的全部理由:

| 顺序                       | 崩在中间                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------- |
| **dispatch → ack**(本 ADR) | 回复已写、声明未确认 → 宿主重驱 → 最坏**重复一次**。可恢复;业务写有 ADR-0048 的稳定幂等键挡住二次提交。 |
| ack → dispatch(修复前)     | 标记完成、什么都没发 → **永久静默,且不可检测**。                                                        |

**在 result 事件时确认(而非流关闭时)本身是对的**,不改:它防止宿主清扫看到"卡住的
processing 声明"而误判——流会为跟进推送保持打开。**只调换块内两行的顺序。**

### 各确认点的复核

- `result` 事件(主路径)——**已修**,本 ADR 的对象。
- **跟进推送路径**——**也已修**(见下方修正段)。这里原本是本 ADR 最大的一个洞,
  而不是可接受的残留:`query.push()` 之后立刻确认,而那批消息的输出要到**之后的**
  result 事件才出现——同一类 at-most-once 洞,窗口不是两条相邻 SQLite 调用,
  而是**整整一个模型回合(秒到分钟)**。
- 强制路由 delegate 路径——`writeDirectDelegation` 在 `markCompleted` 之前,**本就正确**。
- 回合尾部的兜底 `markCompleted`——在一切之后,无序问题。
- 命令路径(`/clear`)——**确实有用户可见输出**("Session cleared."),但
  `writeMessageOut` 在 `markCompleted(commandIds)` 之前,顺序正确。
  (初稿写作"命令路径按定义无输出",表述错误,已更正。)
- pre-task 脚本跳过项——被跳过的行按定义无输出,立即确认正确。
- `ask_user_question`(`mcp-tools/interactive.ts`)——确认的是**用户的回答行**,
  不是 agent 的输出;该行是宿主写入的入站消息,确认它只是防止回合结束时被重复消费,
  与本不变量无关。

## Consequences

- 关闭两个真实的静默丢消息窗口(result 事件、跟进推送)。
  **交付语义(精确表述)**:回合循环不再在**没有输出**的情况下确认任何行——
  确认只发生在 result 事件之后,而中断、流未产出 result、异常三条路径都**不确认**,
  把行留给宿主重驱。**尚未做到的**:result 事件的排空不区分"这次结果回答的是哪些行",
  所以一个在**已在生成中**的回合尾部被推入的跟进,会被那一次的 result 连带确认,
  而它自己的答案要到下一次 result 才出现——窗口从"总是"缩小到"推送恰好落在生成尾部",
  但类别未消除。要消除需要把结果与行做关联,不在本 ADR 范围。
- 代价是崩溃后可能重复一次回复——**这正是我们要的方向**,且业务侧由幂等键兜底。
- 顺序被测试钉住(反转即红),重构无法悄悄再倒过来。
  **覆盖边界(诚实)**:测试断言的是 **result 事件那一处**的执行序列。
  跟进推送路径**已有独立覆盖**(反转即红,已验证)。
  **delegate 路径仍未被覆盖**——单独反转它不会变红。
  写一个覆盖全部确认点的通用不变量测试需要一套 SQL 序列断言框架,当前不划算;
  记录在此,以免下一个人误以为整条不变量都被机器守着。

## 验证

- `integration.test.ts` · crash-durability ordering(2 例):
  ① 记录 outbound.db 的**实际 SQL 执行序列**,断言 `INSERT INTO messages_out` 的下标
  **小于** `processing_ack ... 'completed'` 的下标——窗口是微秒级,轮询观察不到,
  只能对执行序列本身断言;② 一个从不产出 result 的回合被杀后,声明**未被**标记完成,
  工作仍可重驱。
- 反转顺序后测试 ① 变红(已验证)。
- host 963/963,runner 393/393。

## 附:这条 ADR 的由来值得记下

我原本的计划是"把已经正确的顺序写成文档并加测试"。**注释先写好了,断言的却是一个不成立的事实。**
是那个测试——不是代码审查、不是 CI、不是我的心智模型——发现了反转。
教训:**给一个你"确信成立"的不变量补测试,是发现它不成立的最便宜方式。**

## 修正(2026-08-23,合并前红队:3 视角 14 agent,7 条确认,0 条未核验)

**我修了小洞,把大洞写进文档说"改不了"——而红队证明我的理由是错的。**

初稿把跟进推送路径(`query.push()` 后立即 `markCompleted(keptIds)`)记为"流式设计的固有形态,
非重排可修"的可接受残留。事实上:

- 它是**同一类** at-most-once 洞,窗口**大约六个数量级于**我修掉的那个
  (整个模型回合 vs 两条相邻 SQLite 调用);
- 丢失同样是**永久且不可检测**的:`syncProcessingAcks` 会把 `completed` 的确认同步成
  `messages_in.status='completed'`,而重驱只看 `pending` 行,清扫器只扫 `processing` 声明;
- 触达面比想象的宽:回合中的闩锁只拦 `kind=chat/chat-sdk 且 trigger=1` 的行,
  **定时任务行(`kind='task'`)会直接落进推送路径**;
- 而我给出的"不能改"的两条理由**都不成立**:
  1. 以为推送时确认是防止重复领取所必需——**不是**,`markProcessing` 才是
     (`getPendingMessages` 按"是否存在于 processing_ack"过滤,不看状态);
  2. 以为长时间挂着 `processing` 声明会被清扫器惩罚——**基本不会**,
     `host-sweep` 在心跳晚于**该声明自己的领取时间**时跳过它,而 runner 每个 provider 事件都刷心跳。
     **但这个保护不是无条件的**:初始批在回合开始时领取,之后任一事件都能保护它;
     而跟进批在回合**中途**领取,其领取时间按构造**晚于**上一次心跳,需要一个**后续**事件才被保护。
     若恰逢长时间无事件(慢的非 Bash 工具、长思考),清扫器会 kill-claim 杀容器并重驱整个回合
     ——这是延后确认**新引入**的暴露。修法:推送后立即 `touchHeartbeat()`
     (把工作推入活跃 query 本身就是进展),使跟进批与初始批享有同等保护。

**修法**:`runQuery` 内建一个 `pendingAck` 集合,初始为 initial batch,跟进推送时**并入而非确认**,
在**每个 result 事件后**(输出落盘之后)整体确认并清空。
流未产出 result 就结束时**不确认**——那种情况下这些行本来就没有输出,确认它们正是本 ADR 禁止的事;
留在 `processing`,容器退出后由清扫器重驱(入站重试计数与死信上限照常适用)。
同理,**中断(abort)时回合尾部也不确认**:被切断的回合不会产出它本来要产出的东西。
代价是恢复延迟无上界(要等容器退出),换来的是**重复而非静默丢失**。

**顺带修的**:测试辅助函数 `runPollLoopWithTimeout` **从不真正停止循环**
——`runPollLoop` 一直支持 `config.signal`,helper 却没传,abort 只让 race 提前 reject,
循环与其轮询定时器继续在后台跑、写进后续测试的 DB,并使测试进程无法退出
(我新加的停滞-provider 测试把这个既有泄漏放大成了 10 分钟不退出)。已把 signal 传进去。

其余更正见上方各节(命令路径确有输出、ask_user_question 确认的是入站行、测试覆盖边界)。

## 复核修正(2026-08-23,独立核查 agent 实测 7 项)

核查做了真实验(插桩、逐条还原、单独跑),推翻了我上一轮的三处说法:

1. **我那个"跟进推送"测试是假的**。它断言 `m2` 停留在 `processing`,但该行**根本不是被本测试的
   provider 领取的**——是**前一个测试泄漏的轮询循环**抓走并推送的(插桩显示全程零条本测试
   provider 的 push 记录);单独跑 **8/8 全败**。而"还原后变红"的红信号来自 `waitFor` 超时,
   不是我写的那句断言。**已重写**:用测试自己的 `HoldingProvider` 驱动推送,断言记录到的
   **SQL 执行序列**里没有 `completed`;单独跑 3/3 稳定,还原即红(且红在真断言上)。
2. **我上一轮"修好"的测试泄漏根本没修**。`runPollLoop` 只在 `while(true)` **顶部**检查
   `config.signal`,而 provider 的流一直驻留、永远回不到顶部——删掉我加的那行 `signal,`
   结果一字不差(394 pass,同样耗时)。**已真修**:把 signal 接到 `query.abort()`,
   中断真的能终止在途回合。移除该接线会让整文件 2 挂(已验证),证明它现在是有效的。
3. **延后确认新引入了一条杀容器路径**(见上方修正的第 2 点)——已用推送后刷心跳关闭。

另外确认并修掉:**流未产出 result 时的排空本身就是"确认了却没有输出"**(已改为不确认);
**中断时回合尾部同样不该确认**(已加 abort 守卫)。ADR 里"命令路径无输出""at-least-once 统一"
"测试覆盖范围"三处表述已按实测更正。

诚实残留(已写入 Consequences):result 排空不区分"这次结果回答了哪些行",
推送恰好落在生成尾部时仍会被连带确认。
